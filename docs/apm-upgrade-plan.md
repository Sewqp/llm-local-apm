# 로컬 LLM APM 강화 계획

승인일: 2026-10-26. 대상: 에피드 게임즈의 ‘프로그램 베이스 AI 운영관리’ 채용 공고에 제시할 포트폴리오.

## 목적과 원칙

개발자가 LLM을 일상적인 분석 도구로 사용하면서도 소스 코드, 상세 로그, 유저별 사건 흐름을 통제된 내부 환경에서 다룰 수 있게 한다. APM의 관측 자료와 실제 코드를 연결하여 근거가 있는 조사 결과를 제공한다.

- 기존 실검증과 발견 사례를 기반으로 확장한다. 과거 성공 사례를 새 기능으로 대체하거나 지우지 않는다.
- ‘유출 걱정이 전혀 없다’는 보장 대신, 외부 전송 경로를 제한하고 실제 송신 여부·접근 통제·보존 정책을 검증한다. 로컬 추론만으로 인증, 악성 입력, 로그·백업 접근 문제가 모두 해결되는 것은 아니다.
- 상세 로그와 유저 단위 분석 자체를 다른 APM에는 없는 기능이라고 주장하지 않는다. 이 프로젝트의 강점은 내부 소스까지 연결하는 LLM 조사 흐름과 운영 가능한 통제·검증이다.
- 규칙 기반 탐지, 근거 검색, 모델의 추론, 사람의 확정 판단을 구분한다. 모델이 파일을 찾은 것과 실제 지연의 인과관계를 증명한 것은 다르다.
- 원본 운영 데이터·개인 식별 정보는 기본 학습 자료로 사용하지 않는다. 현재 코드는 검색으로 제공하고, 파인튜닝은 조사 방식과 응답 품질에 적용한다.

## 현재 기준점

현재 구성은 C# 수집 서버, SQLite, React 대시보드, LM Studio 로컬 추론, Graphify 코드 탐색이다. 설정에는 Gemma 4 26B-A4B가 기록되어 있으나 모든 과거 분석 행의 실제 모델·프롬프트 버전이 저장되어 있지는 않다. 현재 장치 조회에서는 RTX 4080 SUPER, VRAM 16GB를 확인했다. 학습 가능 크기와 속도는 별도 실측한다.

실검증 근거와 한계는 [validation-baseline.md](validation-baseline.md), 평가 사례는 [evaluation/cases.json](evaluation/cases.json)에 둔다. 원본 증거는 Git에서 제외한 `.local-evidence/2026-10-26/`에 보관한다.

## 1. 기존 증거 보존과 평가 기준 정리 — 진행 중

2026-10-26 완료한 범위:

- 서로 다른 위치에 있던 원본 DB 두 개를 읽기 전용으로 열어 일관된 SQLite 사본을 생성했다.
- 분석 성공·실패 행, 스크린샷, 원본 시연 영상, 관련 코드·설정·그래프·Git 상태, 당시 대화와 메모리의 관련 기록을 보존했다.
- SHA-256 목록, 데이터 집계, 발견별 근거와 주장 가능한 범위를 작성했다.
- 평가 사례 목록을 작성했다. 아직 자동 평가 실행 결과나 파인튜닝 정답 데이터셋은 아니다.

다음 작업:

1. 평가용 DB와 서버를 분리하고, 테스트마다 `run_id`, 소스 리비전/변경분 해시, 모델·프롬프트·설정 버전을 남긴다.
2. 기존 대표 사례를 재실행할 조건을 고정한다. 서버 빌드 구성, 접속 속도·유지 시간, 분석 창, 기준선 기간, 모델 상태를 기록한다.
3. 실패와 ‘근거 부족’도 남기는 재현 결과표를 만든다. 재실행 전에는 새 성능 수치나 탐지 성공률을 쓰지 않는다.

완료 기준: 보존본 검증 + 대표 사례의 재현 절차 확정 + 통제된 재실행 기록. 현재는 보존·목록화까지 완료했으며 마지막 재실행은 미수행이다.

## 2. 유저·세션·요청을 연결하는 계측

- `run_id`, `trace_id`, `span_id`, `parent_span_id`, 내부 가명 `user_key`, `session_id`, 서버·빌드 버전, 패킷 종류, 결과 분류를 정의한다.
- 요청 전체 시간과 하위 구간을 나눈다: 세션/락 대기, 핸들러, DB 연결 획득·쿼리, Redis, Orleans 호출, 응답 전송. 도메인 실패와 예외를 별도로 기록한다.
- `HeartbeatManager` 전체 스윕 시간·대상 수·개별 Grain 대기 시간을 계측해 기존 구조적 위험을 실제 지연과 비교한다.
- 클라이언트의 로그인·Heartbeat 왕복 시간과 서버 처리 시간을 구분하여 연결한다.
- 무제한 큐와 메트릭별 HTTP 전송을 제한된 큐·배치 전송으로 바꾸고, 드롭·큐 길이·전송 실패를 드러낸다. 정상 동작 오버헤드도 측정한다.
- 조회는 권한과 기간·유저 범위를 제한한다. 로그인 토큰, 채팅 원문 등은 목적 없이 수집하지 않는다.

완료 기준: 특정 테스트 유저의 지연 요청을 한 타임라인에서 추적하고, 누락 구간과 수집 오버헤드를 수치로 설명할 수 있다. 기존 지표·분석 사례가 계속 조회된다.

## 3. 근거를 찾아 조사하는 LLM 연결

읽기 전용 도구부터 제공한다: `get_metrics`, `get_trace`, `get_user_timeline`, `search_logs`, `search_code`, `read_code`, `compare_runs`, `get_past_incidents`. 사용자 질문과 권한을 바탕으로 서버·시간·유저 범위를 먼저 정하고 조회한다.

조사 예시: ‘이 유저가 로그인에 실패한 이유를 찾아줘’ → 요청과 도메인 결과 → 관련 로그·하위 지연 → 실제 코드 → 이전 사례 비교 → 근거를 붙인 설명.

- 이상 탐지 건수가 0이어도 수동 조사와 코드 구조 검토를 시작할 수 있게 한다.
- 결과 형식은 `observations`, `hypotheses`, `evidence_refs`, `code_refs`, `unknowns`, `next_checks`로 분리한다. 파일·행·로그·trace 참조는 서버에서 존재 여부와 접근 권한을 검증한다.
- 도구 호출·응답, 사용한 코드 버전, 모델·프롬프트 버전, 소요 시간·실패 사유를 감사 기록으로 남긴다. 토큰 등 민감한 값은 기록 전에 제거한다.
- 후보가 없거나 증거가 부족하면 그대로 답한다. 배경 서비스 탐색은 quick/full 안내문만으로 보장됐다고 간주하지 않는다.
- Graphify 그래프를 소스 리비전과 연결한다. 오래된 그래프는 갱신하거나 오래됐다는 사실을 결과에 표시한다.

완료 기준: 기존 HeartbeatManager 사례, 주입한 DebugHandler 오류, 정상·근거 부족 사례에 대해 실제 도구 근거가 연결되고 추측을 확정 원인으로 표현하지 않는다.

## 4. 내부 처리와 보안 통제 검증

2단계부터 함께 적용하고, 4단계에서 통합 검증한다.

- LLM·임베딩·검색 엔드포인트를 허용 목록으로 제한하고 외부 모델 자동 대체를 두지 않는다. 모델 다운로드·업데이트와 실제 추론 실행의 네트워크 조건을 구분한다.
- 코드 파일은 정규화된 실제 경로가 허용 루트 안에 있는지 확인한다. 경로 순회·절대 경로·링크 우회와 명령 실행 가능성을 검증한다.
- 사용자 인증, 역할별 조회 범위, 가명 ID 대응표 분리, 보존 기간, 감사 로그 접근 권한을 정의한다.
- 로그·코드 안의 문장을 지시가 아닌 자료로 취급한다. 악성 로그가 도구 실행이나 외부 전송을 유도하는 평가 사례를 둔다.
- 외부 인터넷이 없는 조건에서 핵심 흐름을 실행하고, 별도의 송신 관찰 결과로 허용되지 않은 외부 전송이 없었는지 확인한다.

완료 기준: 내부 추론·검색 흐름의 실제 네트워크/접근 테스트 기록, 차단 사례, 알려진 한계를 제시할 수 있다. ‘보안 위험 0’으로 표현하지 않는다.

## 5. 작은 로컬 모델 파인튜닝 실험

1~4단계에서 정답 근거와 실패 유형을 쌓은 뒤 진행한다. 초기 실험 후보는 4B급 모델의 QLoRA이며, E4B를 검토 후보로 둔다. 모델의 정확한 배포판·라이선스·학습 런타임 지원과 16GB VRAM 적합성은 착수 시 확인한다. 학습 성공이나 속도를 현재 확정하지 않는다.

첫 학습 과제는 근거 기반 응답, 후보 순위, 구조화 출력, 근거 부족 판단이다. 도구 선택 학습은 실제 도구 호출 기록과 검증된 예제가 쌓인 뒤 추가한다. 임계값 탐지나 최신 코드 지식 자체를 모델에 외우게 하지 않는다.

- 초기 목표는 사람이 검수한 100~300개 예제이지만, 현재 보존된 20개 분석 행이나 메트릭 119만여 건을 독립된 정답 사례 수로 환산하지 않는다.
- 같은 장애·실행의 변형 문장과 유사 로그는 한 그룹으로 묶는다. 시나리오/실행 단위로 학습·검증·최종 평가를 분리하고, 고정 평가 사례를 학습에 섞지 않는다.
- 잘못된 원인 단정, 파일·행 누락, 대괄호 형식 실패, 도구 없이 추측, 연결 실패, 정상·판단 유보 사례를 포함한다. 실제 비밀·개인정보는 제외한다.
- 같은 기반 모델의 학습 전후를 동일 프롬프트·검색·도구·양자화 조건에서 비교한다. 기존 26B 모델은 별도 참고 기준으로 비교한다.
- 지표: 근거 참조 유효성, 구조화 출력 유효성, 관련 코드 Top-3, 원인 과단정 비율, 판단 유보 품질, 지연·VRAM. 표본 수와 실패 유형을 함께 공개한다.
- 효과가 없으면 학습 모델을 채택하지 않고, 결과와 데이터 한계를 실험 기록으로 남긴다.

완료 기준: 학습 실행 기록, 데이터 구성·분할 근거, 재현 가능한 동일 기반 모델 비교표. 정확도 개선을 주장하려면 평가 결과가 필요하다.

## 6. 사내 도입을 설명할 수 있는 운영 자료

- 모델·프롬프트·도구 버전 등록, 상태/지연/실패 모니터링, 회귀 평가, 업데이트와 복구 절차를 준비한다.
- 설치·장애 대응·보안 정책·직군별 사용 예시를 작성한다. 다른 개발자의 재현 검증은 실제 참여와 결과가 있을 때만 협업 성과로 기록한다.
- Slack/Jira 연동은 내부 정책과 데이터 범위가 정해진 뒤 선택한다. 외부 서비스로 원본 코드·로그를 보내는 자동 연동은 기본 경로로 삼지 않는다.
