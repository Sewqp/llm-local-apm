# HTTP·분산 호출·큐 워커 검증 — 2026-10-26

## 목적과 범위

기존 Orleans/TCP 게임 서버 외에도 APM을 붙이기 위해 [실행 가능한 예제](../examples/ArchitectureDemo/README.md)를 새로 작성했다. 로컬 ASP.NET Core 프로세스 두 개, 실제 SQLite DB 두 개, 별도의 수집 DB를 사용했다. 기존 게임 서버의 추가 3만 동접 검증으로 표현하지 않는다.

Run: `architectures-20261026-205354`. 상세 표본 100%, 동시 HTTP 호출 32개. 원본 결과: `.local-evidence/2026-10-26-architectures/run2/`.

## 구현

- HTTP method, 경로 템플릿, 실제 응답 상태를 기본 메트릭과 진입 span에 저장한다. query/body/Authorization 및 예외 메시지 원문은 수집하지 않는다.
- 미수집 ASP.NET ambient Activity를 부모로 연결하지 않고 종료 후 복원한다. traceparent는 기록된 HTTP client span에서 별도 프로세스의 server span으로 이어진다.
- 큐 작업은 별도 trace에 LinkedTraceId/LinkedSpanId와 가명 유저·세션을 보존한다. 접수부터 완료까지를 루트로 기록하고 queue.wait와 처리 구간을 구분한다.
- HTTP 필터, 서비스별 상세 수집 개수, 작업에서 접수 요청으로 이동하는 링크를 추가했다. 짧은 요청의 시각 소수부가 잘려 타임라인 막대 위치가 어긋나던 표시 문제도 수정했다.
- SourceFile은 설정된 소스 루트의 허용된 .cs 파일만 읽는다. 분산 요청은 최대 세 서비스/파일의 현재 코드·SHA-256·줄 번호를 로컬 LLM 근거에 넣는다. 프롬프트 버전: trace-evidence-v2.
- 실제 수집 소스가 Npgsql인 경우만 PostgreSQL로 표시하여 수동 SQLite span 이름을 보존한다.

준비/비교/오류/큐를 포함한 클라이언트 HTTP 1,074건, 하위 서비스 HTTP 323건, 비동기 작업 9건을 합쳐 **진입 기록 1,406건·기본 메트릭 1,406건·전체 span 8,860개·오류 로그 4개**를 저장했다. 독립 클라이언트 결과, 서비스 카운터, DB를 대조했다. 서비스 간 하위 호출은 추가 사용자 수가 아니다.

두 프로세스 모두 기본/상세 전송 유실, 실패한 전송 시도, 전송 대기 0. 부모 참조와 서비스별 상세 수집 개수 일치. 이 실행의 결과이며 장시간·대규모 부하에서의 보장이 아니다.

큐 65건 중 9건 접수, 56건 HTTP 429. 접수된 작업 8건 완료, 1건 의도적 실패. 실제 Rewards 행 8개. 최대 큐 대기 728.10ms. **HTTP 202 접수 성공과 나중의 워커 실패를 구분**하며 실패 작업에서 원래 접수 요청으로 이동한다.

## 검증과 LLM

- 구조 통합 검사 58개, Agent 33개, API 30개, 소스 경로 제한 5개 통과. .NET 예제/수집 서버와 프런트엔드 빌드 통과.
- 기존 v2 검증 DB 사본을 실제 앱으로 마이그레이션했다. 기존 모든 열의 행 해시 일치: span 23,240, metric 1,837, runtime 609, batch 4,838, log 5, trace investigation 2. 보존 원본 파일 SHA-256 불변, integrity_check 정상.
- UI에서 HTTP 필터, 두 서비스의 상세 수집 상태, 작업에서 원래 요청으로 이동하는 링크를 직접 확인했다.
- 로컬 Gemma 최종 분석: 분산 오류 약 9.12초, 워커 실패 약 6.62초. 각각 RemoteCheckout.cs/StockHandler.cs, RewardWorker.cs와 실제 trace·로그를 받았다.
- Stock 예외 전파와 job.Fail 분기를 원인 후보로 설명했다. 첫 워커 답변은 로그 span을 잘못 인용했고, 재실행은 실제 로그 span을 인용했다. 모두 보존한다. 프롬프트 내용은 같고 버전 표기만 정리한 재실행이므로 정확도 개선 증거가 아니다.
- LLM이 원래 접수 trace를 자동으로 추가 조회하지는 않는다. UI 인과 링크와 작업 근거의 LinkedTraceId까지 제공하는 범위다. 파인튜닝이나 정량 진단 정확도 평가는 수행하지 않았다.

## 중간 실패와 과거 기록

첫 실행은 HTTP/수집 대조 이후 Python 3.10이 .NET의 소수 7자리 타임스탬프를 읽지 못해 검증 스크립트가 중단됐다. 파서를 수정하고 새 DB에서 두 번째 실행을 완료했다. 첫 실행 DB·응답·카운터·검사 목록도 run1에 보존했다. 이 종료와 겹친 Agent live 검사도 중단되었으며, 두 번째 수집 서버에서 33개 전체 검사를 다시 통과했다.

이전 3만 동접 성공, 같은 코드에서 기본 3,154건 유실, 원인 미확정 런타임 정체는 [기존 보고서](apm-reliability-20261026.md)에 그대로 남아 있다. 이번 합성 예제 결과가 대체하지 않는다. HeartbeatManager 실제 순차 구조와 DebugHandler 의도적 오류 구분도 유지한다.

## 남은 한계

외부 호스트/네트워크, 시계 차이 보정, 동일 프로세스 재진입 호출, 영속 브로커, 재전송·재시작 복구, 장시간 최대 처리량, APM on/off 오버헤드는 검증하지 않았다. 메모리 큐와 공개 합성 HMAC 키를 그대로 운영에 배포하는 예제가 아니다. 로컬 수집·추론 경로 및 비밀 표식 미저장을 확인했으며 OS 전체 외부 송신이나 유출 위험 0을 증명하지 않았다.
