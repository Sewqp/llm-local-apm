# CPU 측정 보정과 런타임 정체 조사 — 2026-11-16

CPU가 실제보다 높게 표시되는 계산 오류를 수정했다. 런타임 정체는 별개의 현상이었다. 반복 부하 시험에서 직전 실행의 대량 TCP 연결이 TIME_WAIT에서 사라지는 시점에 호스트 커널 CPU가 급증했고, 게임을 제외한 TCP 시험에서도 같은 급증과 실행 지연이 나타났다. 이전 연결이 정리된 뒤 시작한 3만 동접·120초 시험에서는 정체 경고가 없었다.

이 결과는 **CPU 표시 오류 수정**과 **시험 간 잔여 연결이 측정을 방해하는 조건 확인**이다. Windows 내부의 특정 함수·드라이버까지 확인하거나 모든 런타임 정체를 해결했다는 뜻은 아니다. 이전 검증 문서와 성공·실패 기록은 수정하지 않고, 이번 결과를 별도 추가했다.

## 1. CPU 표시가 틀어지는 이유와 수정

`TelemetrySender.RuntimeLoopAsync`는 프로세스 CPU 누적값을 업로드 **전**, 경과 시간의 기준을 업로드 **후**에 갱신했다. 따라서 다음 측정의 CPU 사용량에는 업로드 대기 중의 사용량이 들어가지만, 분모에는 그 시간이 빠졌다. 업로드가 오래 걸리면 100% 제한값까지 부풀 수 있었다.

CPU 누적값과 `Stopwatch` 기준을 같은 채집 시점에 맞추고, 전송 전에 둘을 함께 갱신했다. 전송 성공 여부와 무관하게 다음 구간의 분자·분모가 같은 기간을 나타낸다. 표시 단위는 기존과 같은 **전체 논리 CPU 용량 대비 프로세스 사용률(0~100%)**이다. 단일 코어를 계속 쓰는 16논리CPU 환경에서는 약 6.25%에 해당한다. API 형식은 바꾸지 않았다.

실제 Agent의 5초 타이머를 사용하고, 첫 HTTP 업로드를 8초 지연하는 동안 한 작업 스레드에 CPU 부하를 줬다. 전송기 진입 시 별도로 읽은 프로세스 누적 CPU와 monotonic 시간으로 비교했다.

| 검사 | 기준 CPU | 보고 CPU | 결과 |
|---|---:|---:|---|
| 수정 전 소스 사본, 지연 전송 | 5.9596% | 100% | 예상대로 회귀 검사 실패 |
| 수정 후, 지연 전송 성공 | 5.9291% | 5.9396% | 오차 0.0105%p, 통과 |
| 수정 후, 지연 후 HTTP 503 | 6.1353% | 6.1318% | 오차 0.0034%p, 통과 |

검사 코드는 [RuntimeCpuChecks](../tools/verification/RuntimeCpuChecks/RuntimeCpuChecks.cs), 수정은 [TelemetrySender](../src/Apm.Agent/TelemetrySender.cs)에 있다. 기존 Agent 검사도 30/30 통과했다. 구버전은 별도 사본으로 빌드했으며 현재 작업 트리를 되돌리지 않았다. 서버·수집기·부하 도구 빌드도 통과했다. 이번 빌드는 NuGet 보안 감사 결과를 의미하지 않는다.

## 2. 런타임 정체를 조사한 조건

Windows의 동일 PC에서 서버와 부하 발생기를 함께 실행했다. Ryzen 7 7800X3D, 논리 CPU 16개, 물리 메모리 약 31.1GiB, .NET 10 SDK 10.0.301, Orleans Runtime 10.3.1 환경이다. 실행마다 별도 PostgreSQL DB, Redis 인스턴스, APM SQLite를 사용했다. 원래 DB·사용자 서비스는 초기화하거나 종료하지 않았다.

각 게임 시험은 1,000 연결 준비 실행 후 30,000 로그인, 5초 간격 Heartbeat, 60초 또는 120초 유지로 구성했다. 게임·부하 발생기에 선택적 startup hook을 붙여 100ms 간격 전용 스레드에서 CPU·GC 정지 시간·ThreadPool 대기·작은 작업의 실행 지연을 기록했다. 별도 Python 프로세스는 Win32 CPU 누적값, PDH 커널 CPU, 메모리, TCP 상태를 관찰했다. 관찰 코드 자체의 비용도 포함된 결과다.

중단·재개 사이에 PC의 다른 작업과 가용 메모리가 달라졌다. 따라서 아래 실행들을 APM 성능 향상률을 계산하는 통제된 ON/OFF 비교로 사용하지 않는다. 목적은 정체가 나타나는 조건을 분리하는 것이다.

| 실행 | 조건 | 3만 유지 | Heartbeat RTT p99 | Orleans 실행 지연 경고 |
|---|---|---:|---:|---|
| diag01_on | APM ON | 60.003초 | 76.02ms | 없음 |
| diag02_off | APM OFF, 앞선 연결 만료와 겹침 | 60.005초 | 1,322.28ms | Thread Pool 1.034초 |
| diag03_off_host | APM OFF, 긴 중단 후 재개 | 60.009초 | 14.39ms | 없음 |
| diag04_off_overlap | APM OFF, 앞선 연결 만료와 겹침 | 120.014초 | 434.26ms | Thread Pool 4.277초 |
| diag05_off_guarded | APM OFF, 잔여 연결 사전 검사 | 120.000초 | 8.50ms | 없음 |

다섯 실행 모두 유지 구간의 최소 로그인 수는 30,000이고 클라이언트 기능 검사를 통과했다. 이는 로그인·Heartbeat 시험이며 가챠·길드·매칭이 섞인 실사용 최대 처리량 검증은 아니다. 위 RTT는 클라이언트가 관찰한 왕복 시간이며 서버 핸들러 처리 시간과 다르다.

APM ON 실행의 저장 대조는 준비 실행 포함 로그인 **31,000건**, Heartbeat **426,869건**, 합계 **457,869건**이 일치했다. 첫 자동 대조는 배경 작업 metric까지 패킷으로 세어 실패했다. 당시 `ledger.json`과 실패 종료 기록을 남겨 두고, `Method='PACKET' AND RunId=...`로 한정한 재분석 결과를 새 `analysis.json`에 저장했다. 이 검사 오류를 서버 요청 실패나 telemetry 유실로 해석하지 않는다. 후속 하네스에는 수정된 대조 조건을 반영했다.

## 3. 정체 원인을 좁힌 근거

### 과거 12회 기록에서 반복되는 시점

[11월 10일 원본 비교](apm-ab-comparison-20261110.md)를 다시 읽었다. 첫 실행에는 정체가 없었고, 정체가 있었던 이후 11회 모두 이전 실행 종료 약 120초 뒤의 대량 TIME_WAIT 감소 구간과 겹쳤다. 해당 실행들의 호스트 커널 CPU 최대치는 약 84~97%였다. 과거의 실행 간 30초 대기는 TCP 연결 정리가 끝났다는 조건이 아니었다.

예를 들어 `ab-clean-03-after-off`는 이전 실행이 08:58:35 UTC에 종료된 뒤, 09:00:33~44 UTC 관찰 구간에서 커널 CPU 92.74%를 기록했다. 같은 구간의 게임 프로세스 CPU는 전체 CPU 기준 약 0.062%, 부하 발생기는 0.285%였다. TCP TIME_WAIT는 약 31,000개에서 1,000개 수준으로 줄었다. 게임 코드가 CPU를 모두 소비하는 상황과 구분된다.

이는 과거 원시 기록을 재해석한 결과다. 12회를 새 프로토콜로 전부 재실행한 것은 아니다. 과거 요청·저장 건수 및 오류 기록은 그대로 유효한 관측으로 보존하되, 당시 CPU·메모리·지연 차이를 순수 APM 비용이나 코드 개선의 인과 효과로 단정하지 않는다. 외부 Win32 CPU를 사용했으므로 옛 보고서의 CPU 산식과 이번 Agent 표시 오류도 구분한다.

### 게임 서버에서 재현

`diag04_off_overlap`의 13:10:28~31 UTC 구간에서 이전 실행의 TIME_WAIT가 줄어들며 커널 CPU가 **99.50%**, 프로세서 대기열이 최대 **299**까지 올라갔다. Orleans는 **4.277초 Thread Pool 실행 지연**을 남겼다. 같은 문제 구간의 500ms 이상 관찰 지연에서는 게임의 GC 누적 정지 시간이 증가하지 않았고, 게임·클라이언트·외부 관찰자도 함께 늦어졌다.

따라서 해당 구간을 게임 GC만의 문제나 단순 ThreadPool 최소 스레드 부족으로 설명하기는 어렵다. Thread Pool 경고 자체도 실행이 늦었다는 관측이며 원인 확정 메시지가 아니다. 다른 시점에는 약 485ms GC 정지를 포함한 지연도 실제 관찰됐으므로 GC 영향 전체를 배제하지 않는다.

### 게임을 제거한 최소 TCP 시험

[TcpExpiryProbe](../tools/verification/TcpExpiryProbe/TcpExpiryProbe.cs)는 loopback TCP 연결 30,000개를 열고 정상 종료한 후 기다린다. 게임·Orleans·DB·APM은 실행하지 않았다. 만료 구간에는 TCP 목록을 반복 조회하지 않았다.

- 연결 종료: **13:14:59.307 UTC**.
- 커널 CPU 정점: **13:16:59.092 UTC**, 종료 약 **119.78초 후 96.28%**.
- 전체 TIME_WAIT: 종료 직후 **30,047 → 최종 49**.
- 전용 관찰 스레드의 최대 간격: **380ms**(설정 100ms), 해당 지연 구간 GC 정지 증가 **0ms**.

게임이 없어도 대량 연결의 만료 시점에 커널 CPU 급증과 실행 지연이 나타났다. 다만 이 최소 시험의 지연은 380ms였으며, 서버 시험의 4.277초 경고 전체를 같은 크기로 재현했다고 표현하지 않는다. 정확한 커널 함수·네트워크 필터·드라이버의 책임을 구분하려면 커널 스택을 포함한 별도 추적이 필요하다. 이번에는 그 추적을 수행하지 않았다. 이 PC에서 관찰한 약 120초를 모든 Windows 환경의 고정값으로 일반화하지 않는다.

## 4. 반영한 조치와 대조 결과

게임 서버의 GC 모드·ThreadPool 설정·Redis/SQL 저장 구조를 바꾸지 않았다. 먼저 시험 절차에 **이전 연결 정리 확인**을 추가했다. 호스트 전체 TIME_WAIT가 2,000 미만인 상태를 2초 간격 두 번 확인한 뒤 시작한다. 최대 300초 동안 조건이 충족되지 않으면 부하를 시작하지 않는다. 2,000은 이 3만 연결 실험의 잔여 부하를 구분하기 위한 기준이며 운영 안전 한도가 아니다.

이 절차를 사용한 `diag05_off_guarded`는 시작 전 TIME_WAIT **47개를 두 번 확인**했다. 30,000 로그인 상태를 **120초 유지**, 클라이언트 기능 검사 통과, Orleans 정체 경고 없음, 관찰 스레드 최대 간격 **247ms**, Heartbeat RTT p99 **8.50ms**였다. 이 실행의 메인 관찰 구간에는 커널 CPU 75% 초과 표본도 없었다.

앞선 연결 정리를 기다리면 시험 시간이 늘어난다. 대신 이전 실행의 후처리가 다음 실행의 비용에 섞이는 것을 줄인다. 이번 대조는 단일 실행이므로 무정체를 보장하지 않는다. 물리적으로 분리한 부하 발생기와 동일 환경의 반복 비교는 여전히 필요하다. OS TIME_WAIT 설정을 줄이거나 사용자 프로그램을 강제 종료하는 방식은 적용하지 않았다.
