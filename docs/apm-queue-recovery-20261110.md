## 코드 변경

- `TelemetryBatchWriter`: 단일 연결과 prepared SQL 재사용, 사전 생성한 속성 접근 함수, 512MiB 캐시. receipt·span·metric·log·runtime을 한 트랜잭션으로 저장한다. 같은 BatchId 재전송은 삽입하지 않고 성공 응답한다. `APM_INGEST_TIMINGS=1`이면 대기/삽입/commit 시간만 진단 출력한다.
- `TelemetryCheckpointService`: 1초 주기의 별도 연결에서 PASSIVE 체크포인트. writer의 `synchronous=FULL`과 커밋 후 응답은 유지한다. SQLite 3.51.3+ 실행을 확인하며 native 패키지를 3.53.3으로 고정했다. [SQLite WAL 설명](https://sqlite.org/wal.html), [체크포인트 정의](https://sqlite.org/pragma.html#pragma_wal_checkpoint).
- `TelemetrySender`: 기본 배치 256→1024. HTTP 2,000,000 bytes / logs 1024 제한은 유지하고 큰 배치를 나눈다. 기본 큐 포화 시 여러 미전송 요청을 묶어 스풀에 저장한다. 실패 배치를 버리기 전에 디스크 보관을 시도한다.
- `TelemetrySpool`: 파일 flush→원자적 rename, 동일 BatchId 재전송, 커밋 확인 후 삭제, 시작 시 미전송 배치 재개, 단일 소유자 잠금. 기본 한도 256MiB / 8192배치이며 오류/한도 초과는 명시적으로 집계한다.
- runtime API·스키마·대시보드: 디스크 대기 건수/배치/크기, 복구 건수, 보관 실패를 추가한다. 기존 행에는 0 기본값만 추가한다.
- Trickcal `ApmReporter`: `.apm-spool`을 기본 사용하며 `APM_SPOOL_DIRECTORY`로 배포와 분리된 경로를 지정할 수 있다. 공용 Agent의 다른 사용처는 `SpoolDirectory`를 명시해야 한다.

## 검증과 범위

Agent 회귀, 실제 HTTP 계약, 저장 중간 실패의 원자적 롤백/재시도, 동시 writer, 큐 초과·응답 유실·Agent 재생성 후 디스크 복구·한도 초과·Unicode byte 제한 검사를 수행했다. 각 결과 JSON은 비공개 증거에 보존한다.

최종 게임 프로세스 최대 working set은 약 2754MiB, 수집기는 783MiB였다. 기본 큐는 종료 후 0이며 스풀도 비었다. 관측된 최저 시스템 가용 메모리는 7926MiB였다.

Windows 16 logical CPU / 메모리 약 31GiB / loopback / Release에서 새 계정 로그인 후 5초 간격 Heartbeat를 보낸 시험이다. PostgreSQL 18.4, Windows Redis 3.0.504(AOF everysec), SQLite 3.53.3을 사용했다. 가챠·극장·길드 전체 기능이 동시에 3만 명에게 실행되는 부하는 이번 범위에 포함하지 않는다. LLM 추론도 실행하지 않았다. 정상 부하에서는 디스크 fallback을 쓰지 않았으며, 복구 동작은 별도 장애 주입 검사의 결과다.

스풀은 저장된 배치의 복구 수단이다. 강제 종료 순간 메모리에만 있던 항목, 디스크 용량 소진, 무제한 장애를 보장하지 않는다. 긴 조회로 체크포인트가 진행되지 않으면 WAL이 커질 수 있어 디스크 여유와 수신 지연을 함께 관찰한다. 이전 두 무손실 실행의 CodeVersion 환경 태그는 기존 값을 유지했으며, 실제 실행 코드 구분은 증거의 바이너리 SHA-256을 따른다. 최종 Run의 태그는 `apm-queue-recovery-working-tree-20261110`이다.
