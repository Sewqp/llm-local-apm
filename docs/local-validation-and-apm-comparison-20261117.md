# 로컬 정합성 검사와 APM ON/OFF 반복 측정 — 2026-11-17

새 APM CPU 수정 버전을 연결한 서버로 로컬 검사를 통과한 뒤, ON/OFF 각각 3회 부하를 실행했다. 이전 실행의 대량 TCP 연결 정리가 다음 실행과 겹치지 않도록 사전 검사를 적용했다. 과거 검증은 수정하거나 이번 집계에 섞지 않았다.

**이번 결과는 Windows 로컬 검증이다.** 사용자 선택에 따라 추가 업로드와 GitHub Actions 실행은 하지 않았다. 서버 CI 파일 두 개의 APM 참조 및 CPU 검사 추가는 로컬 커밋에만 있으며, 원격 main에는 반영되지 않았다. 리눅스 systemd 배포·롤백을 다시 검증한 결과도 아니다.

## 검증한 소스와 환경

- 게임 서버 체크아웃: `a194c67493a0ff54c4953885e0103602b253e58d`(로컬 커밋). 게임 로직은 기존 원격 `e45702fc1bdc49ae5ffe198478beb51062a75833`과 같고, 차이는 CI 파일 두 개다. 사용자 작업 중인 ScenarioClient·docker-compose 변경은 별도 체크아웃에 포함하지 않았다.
- APM: `0e37c6350168a6abcc69339efae1839aacfe295b`. CPU 누적값과 경과 시간 기준을 같은 시점으로 맞춘 버전이다.
- 같은 Windows PC, 논리 CPU 16개, .NET 10.0.301, PostgreSQL 18, Windows Redis. 서버·부하 발생기·수집기를 같은 호스트에서 실행했다. 다른 사용자 프로그램은 종료하지 않았다.
- 테스트용 PostgreSQL 클러스터·실행별 DB, 별도 Redis, APM SQLite를 새로 만들었다. 원래 DB를 초기화하거나 기존 서비스를 종료하지 않았다. 원시 파일과 바이너리 SHA-256은 비공개 manifest로 연결한다.

## 먼저 실행한 로컬 검사

| 검사 | 실제 결과 |
|---|---|
| Release 빌드 | 서버·수집기·부하 도구·정합성 검사·CPU 검사 빌드 통과 |
| 서버 정합성·저장·Orleans·TCP 통합 | 40,298 assertions 통과 |
| 실제 GameServer 강제 종료·재시작 | 가챠 응답 재사용, 재화 차감·보상 1회, 전투력 대조 통과 |
| CPU 회귀: 8초 지연 업로드 성공 | 오차 0.0205%p, 통과 |
| CPU 회귀: 8초 지연 후 HTTP 503 | 오차 0.0085%p, 통과 |

40,298은 반복 조건을 포함한 assertion 수이며 독립 시나리오나 사용자 수가 아니다. 강제 종료 검사는 Redis·SQL을 유지하고 게임 프로세스만 종료한다. Redis 자체 유실이나 호스트 장애 복구까지 검증한 것은 아니다. 로컬 빌드는 `NuGetAudit=false`로 실행했으므로 보안 감사 통과로 표현하지 않는다.

## 반복 측정 절차

순서는 **OFF → ON → ON → OFF → OFF → ON**으로 미리 정했다. 각 실행은 새 데이터에서 1,000 연결·10초 준비 후 30,000 로그인 연결을 120초 유지한다. Heartbeat는 응답 후 5초를 기다리는 방식이다. 게임·수집기·클라이언트 바이너리는 여섯 실행에서 동일하다. APM ON은 기본 요청 전량 저장, 정상 상세 1% 선택 정책을 사용했다.

실행 전 전체 TIME_WAIT가 2,000 미만인 상태를 2초 간격 두 번 확인했다. 직전 본 부하의 약 3만 연결이 남아 있으면 최대 300초 기다리고, 정리되지 않으면 실행하지 않는다. 이 값은 이번 시험의 대량 잔여 연결을 구분하는 기준이며 운영 안전 한도가 아니다. 같은 실행의 1,000 연결 준비 단계에서 발생한 TIME_WAIT까지 0으로 만드는 조건은 아니다.

외부 Win32 누적 CPU와 monotonic 실행 기록을 수집했다. CPU는 UTC 유지 구간 경계를 둘러싼 관찰값을 선형 보간해 누적 차이를 구하고, 실제 구간 길이와 논리 CPU 16개로 나눴다. 메모리는 구간의 시간 가중 평균이다. 아래 표는 **실행별 값 3개의 중앙값(최소~최대)**이며 전체 요청을 합쳐 다시 계산한 분위수가 아니다. CPU 100%는 호스트 전체 용량, 1코어 사용은 약 6.25%다.

## 해석과 남은 한계

- 앞선 11월 10일 측정에 나타난 대량 TIME_WAIT 만료의 겹침을 줄여 다시 관찰한 결과다. 당시 수치와 실패 기록은 그대로 보존한다. 하드웨어에서 실행 중인 다른 작업, 가용 메모리, 시험 길이·소스 조건이 같지 않아 두 날짜의 차이를 코드 수정의 성능 향상률로 계산하지 않는다.
- 같은 PC에서 부하를 만들기 때문에 클라이언트 타이머·CPU 경합이 RTT와 응답률에 영향을 준다. 물리적으로 분리한 발생기의 반복 비교는 남아 있다. 호스트 전체 CPU와 게임 CPU를 구분한다.
- 비용 표는 120초 유지 구간을 대상으로 하며 연결 종료 뒤의 OS 정리 비용은 포함하지 않는다. 대기 절차는 그 비용이 다음 실행에 섞이지 않게 하는 조치다. Windows의 대량 TIME_WAIT 정리 부하 자체를 수정하거나 없앴다는 뜻은 아니다.
- 로그인·Heartbeat 부하다. 가챠·성장·매칭·길드가 섞인 실제 콘텐츠 부하나 장시간 운영 비용은 확인하지 않았다. 관찰용 startup hook과 외부 관찰자 자체의 비용도 포함된다.
- 응답 후 기다리는 closed-loop 부하의 응답/초를 서버 최대 TPS로 표현하지 않는다. 기존 CPU 표시 오류 수정은 측정의 정확성을 고친 것이며 게임 처리 속도를 직접 개선한 변경은 아니다.
- 중요한 재화와 요청 ID의 SQL 원자적 저장, Heartbeat 통계 집계, OpenTelemetry 동조건 비교, 준비 상태 검사·외부 알림은 이번 변경에 포함하지 않았다.
