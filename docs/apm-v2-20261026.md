# Local APM v2 — 구현 및 검증 기록

> 후속 19시대 검증: [3만 동시 접속 결과](concurrency-validation-20261026.md). 서버 동접·60초 유지는 통과했지만 APM 전량 수집은 실패했다. 아래 800건 결과는 작은 부하의 결과이며, 최신 확장성 판단에는 후속 기록을 함께 사용한다.

2026-10-26. C# 게임 서버의 요청을 내부 호출·오류·유저별 흐름과 연결하고, 선택한 요청의 관측값과 현재 코드 근거를 로컬 LLM에 제공하는 버전을 구현했다. 실제 게임 서버와 격리된 PostgreSQL/Redis로 검증했다. 상용 APM과의 비교는 공식 문서에 근거한 기능 비교이며, 상용 제품을 함께 실행한 성능 벤치마크는 아니다.

기존 증거는 [validation-baseline.md](validation-baseline.md)에 그대로 보존한다. 아래는 그 이후 새로 수행한 작업이다. 에피드 게임즈의 실제 서버를 대상으로 한 결과가 아니다.

## 1. 상용 APM 기준과 이번 구현

Elastic은 transaction, span, trace, error, metric을 구분하고 요청의 지연과 실패를 내부 구간과 연결한다. [Elastic 데이터 모델](https://www.elastic.co/docs/solutions/observability/apm/data-types), [Transactions 화면](https://www.elastic.co/docs/solutions/observability/apm/transactions-ui).

Datadog의 trace 화면은 waterfall, 연관 로그 및 인프라 지표를 제공한다. 이 조사 흐름을 이번 구현의 비교 기준으로 삼았다. [Datadog Trace View](https://docs.datadoghq.com/tracing/trace_explorer/trace_view/).

| 항목 | 이번 구현 | 범위·차이 |
|---|---|---|
| 요청 추적 | Trace/Span/Parent ID, 실행 ID, 인스턴스, 코드 버전 | 게임 서버 PacketDispatcher부터 응답까지. 인터넷 구간의 RTT는 별도 클라이언트 측정 |
| 내부 병목 구간 | 핸들러, 세션 잠금 확인, Grain, PostgreSQL, Redis, 전송 잠금/송신 | 실제 로그인에서 부모 연결 확인. 여러 프로세스·여러 Silo를 넘는 전체 경로는 미검증 |
| 추적 탐색 | 기간·서비스·요청·결과·가명 유저·세션 필터, 페이지 이동 | 요청당 최대 500 span/100 로그. 잘림·부모 누락 표시 |
| 처리량·지연·오류 | SQL 집계, p50/p95/p99, 서버 오류와 업무 거절 분리 | TCP 결과를 APM용 상태값으로 변환. 실제 HTTP 상태코드가 아님 |
| 오류 연계 | Trace/Span에 예외 타입·스택 연결 | 예외 원문 메시지, 패킷 본문, SQL 값, Redis 키는 수집 대상에서 제외 |
| 실행 자원 | CPU, working set, GC 힙, ThreadPool, 세션 수 | 5초 간격 프로세스 지표. 머신 전체·컨테이너 인프라 분석은 없음 |
| 수집 신뢰성 | 제한된 비동기 큐, 배치, 타임아웃, 재시도, 중복 배치 방지 | 장애 시 유실 가능. 유실/실패 시도/큐 길이를 화면에 표시 |
| 원인 조사 | 선택한 trace + 오류 + 허용된 현재 코드 → LM Studio | 근거 JSON, 모델 이름, 프롬프트 버전, 응답, 소요 시간 보존 |
| 운영 체계 | 로컬 접근 제한, 선택적 보존기간, 기존 DB 비파괴 확장 | RBAC, 다중 조직, SLO, 알림/인시던트 관리, 자동 복구는 미구현 |

유저별 분석이나 내부 설치 자체가 상용 APM에 없는 기능이라는 주장은 하지 않는다. 이 프로젝트의 초점은 **직접 만든 게임 서버의 실행 근거와 내부 소스를 로컬 LLM 조사 과정에 연결한 구현·검증**이다.

## 2. 구현 구조

```text
TCP PacketDispatcher
  └─ Activity: 요청 → 잠금 확인 → 핸들러 → PostgreSQL/Redis/Grain → 응답
       └─ Apm.Agent ActivityListener
            └─ bounded Channel → batch HTTP → CollectionServer → SQLite
                                                  ├─ 집계·추적·오류·자원 API → React
                                                  └─ 근거 스냅샷 + 현재 코드 → LM Studio
```

.NET ActivitySource/Activity의 부모 관계를 사용한다. 기존 Npgsql/Orleans/Redis 계측에서 발생한 Activity도 수집한다. 수집 프로토콜은 프로젝트 전용 JSON 배치이며, 이 CollectionServer가 범용 OTLP 수신기인 것은 아니다. [OpenTelemetry .NET 계측](https://opentelemetry.io/docs/languages/dotnet/instrumentation/).

- `src/Apm.Agent`: 기본 큐 8,192개, 배치 128개, flush 250ms, HTTP timeout 2초, 최대 2회 전송 시도. 종료 시 최대 5초 drain. 동일 재시도의 Batch ID를 유지한다.
- `POST /api/telemetry/batch`: 크기·ID·시간·결과 검증 후 SQLite 트랜잭션 저장. 같은 Batch ID 재전송을 중복 집계하지 않는다. 다른 ID로 다시 전송한 동일 metric까지 전역 중복 제거하는 보장은 없다.
- `GET /api/metrics/summary`, `/timeseries`: 최근 구간을 DB에서 집계한다. p50/p95/p99는 nearest-rank이며, 백그라운드 sweep은 클라이언트 처리량에서 제외한다.
- `GET /api/traces`, `/{traceId}`, `/runtime`: 조회 상한과 필터를 적용한다. 시간은 새 API에서 UTC 오프셋을 명시한다.
- `POST /api/traces/{traceId}/investigate`: 수동 요청 조사. 한 번에 하나의 조사만 수행하고, 모델에 전달하는 span/log/code 양을 제한한다.
- 원래 이상탐지 경로도 유지한다. 서버별 그룹 분리, 0에 가까운 기준선 표시, 후보 경로 검증을 보완했다.

### DB 지연 사례 — 의도적 주입

격리 DB의 `player` 테이블에 ACCESS EXCLUSIVE lock을 약 800ms 유지한 상태에서 실제 로그인 패킷을 보냈다. 잠금 해제 후 정상 로그인했고, trace `cbf7ed75e13dff3a66562bcc8231dc8e`에서 다음을 관측했다.

- 클라이언트 RTT **814.8957ms**
- 서버 요청 **814.7835ms**
- PostgreSQL span **810.3540ms**

이는 내부 DB 구간이 요청 지연을 차지한다는 계측 검증이다. 새로운 자연 발생 버그를 발견했다거나 DB를 최적화했다는 결과가 아니다.

### 작은 부하 실험

단일 로컬 실행, 16 TCP 연결, 각 50 Heartbeat, 클라이언트 간격 2ms. 전체 0.3336초, 클라이언트 처리율 약 2,398회/초, RTT p50 **0.3154ms**, p95 **0.5350ms**, p99 **0.6551ms**. 800 응답과 800 수집 요청 metric이 일치했다. 계측 ON/OFF 비교가 없으므로 오버헤드나 최대 수용량을 주장하지 않는다.

개발 도중 수집기를 중지·재빌드한 구간에는 에이전트가 유실과 실패 시도를 기록했다. 이 누적 수치는 숨기지 않고 인스턴스별 화면에 표시한다. 정상 부하 구간의 800/800 결과와 전체 작업 시간 동안의 무손실 주장을 혼동하지 않는다.

### 로컬 LLM 실제 실행

LM Studio, `google_gemma-4-26b-a4b-it` (기존 설치 Q3_K_S), context 12,288, GPU offload 0.7, 병렬 1, localhost:1234. 새 모델 다운로드나 파인튜닝은 하지 않았다.

동일한 DebugHandler 오류 trace `e8fe3e78f0c0dd1054c4ae46d9c1568e`로 두 번 실행했다.

1. 추적·오류만 제공: **13.16초**. InvalidOperationException 및 일반적인 상태 문제 후보를 설명했다.
2. 추적·오류와 현재 DebugHandler 코드 제공: **13.26초**. **재화 지급 후 관리자 권한을 검사하는 순서 문제**를 지적했다.

이 두 실행은 독립적인 정답 사례 두 개나 통계적인 정확도 비교가 아니다. 코드에 의도적 오류를 설명하는 주석도 포함되어 있으므로 일반화된 버그 탐지 능력의 증명이 아니다. 모델이 원문 로그를 잘못 인용한 부분도 있어 인용 정확도는 실패 사례로 남긴다. 분석은 사람의 코드 확인을 돕는 후보이며, 자동 수정·실행으로 연결하지 않았다.

각 조사에 전달한 JSON, 코드 상대 경로와 SHA-256, 현재 소스라는 표시, 모델 이름, 프롬프트 버전, 응답과 지연을 보존했다. 코드 스냅샷은 **분석 시점 코드**이며 실행 당시 빌드와 일치한다는 보장은 없다.

## 5. 데이터 경로와 남은 한계

- 새 에이전트의 collector 주소와 CollectionServer의 LLM 주소는 loopback HTTP(S)만 허용하고 redirect를 따라가지 않는다. CollectionServer는 loopback 접속/Host 및 허용 Origin을 검사한다. 외부 endpoint와 다른 Origin 거부를 테스트했다.
- 유저 식별자는 HMAC-SHA256 가명 키다. 기본 키는 프로세스마다 임의 생성되므로 재시작 전후 같은 유저를 연결하지 못한다. 연속 추적이 필요하면 `APM_USER_HASH_KEY`를 UTF-8 32바이트 이상으로 지정하고 안전하게 관리한다. 가명화는 익명화와 다르다.
- 수집 로그에는 예외 원문 대신 타입·제한된 스택을 사용한다. 코드·근거·분석 결과가 담긴 SQLite는 여전히 민감한 내부 자료로 취급한다.
- 코드 조회는 설정된 소스 루트 안의 C# 파일만 허용하고 상위 경로/링크 우회를 제한한다. 설정 파일은 이 경로에서 조회하지 않는다. 전체 보안 감사나 OS 방화벽 차원의 송신 차단을 완료한 것은 아니다. 기존 게임 서버의 별도 OTLP exporter 경로도 남아 있으므로 배포 환경에서 함께 점검해야 한다.
- 로그인된 로컬 사용자의 파일 접근, 악성 프로세스, 백업/동기화, LM Studio 자체 설정까지 이 애플리케이션이 통제하지 않는다. **‘유출 위험 0’은 주장하지 않는다.**
- 신규 span/log/runtime/investigation/receipt 보존기간은 `Telemetry__RetentionDays` 1~365로 선택 설정한다. 기본은 자동 삭제 없음. 기존 Metrics/Analyses는 보존기간 작업에서 삭제하지 않는다.
- 일반 OTLP 수집, 다중 서비스 전체 추적, tail sampling, 저장소 분산/장기 다운샘플, SLO/알림/인시던트 관리, RBAC는 후속 범위다.
- 기존 Graphify 캐시는 코드 리비전 변경 자동 무효화가 없고, 기존 이상탐지에는 넓은 데이터 조회 경로가 남아 있다. 모든 LLM 도구 호출의 개별 입출력 감사 기록과 정확한 모델 파일 digest도 아직 없다.

## 6. 파인튜닝 연결 위치

현재 근거 스냅샷과 응답 저장 기능을 **사람이 검수하는 평가·학습 자료의 입력 경로**로 사용한다. 학습 과제는 원인 후보 정렬, 정확한 근거 인용, 구조화 출력, 근거 부족 시 판단 유보다. 최신 코드 자체를 모델에 암기시키거나 탐지 임계값을 학습으로 대체하지 않는다.

먼저 기존 12개 사례를 고정 회귀 평가로 실행하고, 이번 사례의 잘못된 로그 인용도 평가 항목으로 추가한다. 동일 실행/장애 변형은 한 그룹으로 묶어 학습·검증에 나누어 넣지 않는다. 현재 분석 행 수만으로 충분한 학습 데이터라고 말하지 않는다. 작은 모델 QLoRA와 학습 전후 비교는 [강화 계획 5단계](apm-upgrade-plan.md)의 후속 실험이며 이번 구현 완료 범위에 포함되지 않는다.

## 7. 재실행과 증거 위치

[실행·검증 안내](apm-v2-runbook.md)를 따른다. 비공개 검증 DB, JSON 결과, 실제 LLM 응답, 화면, 해시는 `.local-evidence/2026-10-26-upgrade/manifest.json`에 보존한다. 기존 `.local-evidence/2026-10-26/`는 별도로 유지한다. 공개 제출 시 DB/개인 설정을 그대로 첨부하지 않고 이 문서의 검증 범위와 선별된 화면을 사용한다.

포트폴리오 요약 문장:
