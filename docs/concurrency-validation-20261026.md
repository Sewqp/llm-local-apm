# APM v2 동시 접속 검증 — 2026-10-26

## 판정

**게임 서버의 3만 동시 로그인·60초 유지 검증은 통과했다. APM의 해당 요청 전량 수집 검증은 실패했다.** 두 결과를 구분한다. 앞선 800건 검증만으로 3만 규모의 수집 성능을 보장할 수 없으며, 이번 시험으로 실제 수집 한계가 확인됐다.

실행 시각: 2026-10-26 19:09~19:12 KST. 원래 게임/관측 DB는 초기화하지 않았고, 앞서 만든 별도 PostgreSQL·Redis 및 검증용 수집 DB를 사용했다. 이전 3만 동접 증거와 다른 **새로운 실행**이다.

## 조건과 관측 방법

| 항목 | 조건 |
|---|---|
| 환경 | 같은 Windows PC의 loopback, RAM 약 31.11GiB, 단일 게임 서버 |
| 빌드 | 게임·수집기 Debug, 부하 도구 Release, .NET 10 |
| 접속 | 실제 TCP 연결, 각 연결에서 새 시험 계정 생성·로그인 |

기존 DummyClient의 `connected`는 누적 연결 수여서 최대 동접과 유지 여부를 직접 증명하지 못했다. 새 `tools/verification/ConcurrentLoad`는 현재 TCP 연결/로그인 수, 최대값, 유지 구간 최소값, 종료 원인, 클라이언트 RTT를 기록한다. 각 실행은 별도 Run ID로 서버와 연결했다.

추가로 Windows `GetExtendedTcpTable`에서 **해당 게임 서버 PID·로컬 포트 9129의 ESTABLISHED 연결**을 약 10초 간격으로 집계했다. APM이 유실돼도 클라이언트 로그와 OS 연결 수는 별도로 남는다. APM 자원 샘플의 세션 수도 대조했다.

### 클라이언트에서 실제 측정한 RTT

전체 성공 응답으로 계산한 nearest-rank 분위수다. 아래 값은 유실된 APM 표본에 의존하지 않는다.

| 요청 | 표본 수 | p50 | p95 | p99 | 최대 |
|---|---:|---:|---:|---:|---:|
| 1천 명 로그인 | 1,000 | 6.3494ms | 253.8069ms | 352.3927ms | 534.4434ms |
| 1천 명 Heartbeat | 3,000 | 0.1468ms | 0.2545ms | 0.6548ms | 0.7934ms |
| **3만 명 로그인** | **30,000** | **1.8486ms** | **74.1362ms** | **245.6607ms** | **658.8023ms** |
| **3만 명 Heartbeat** | **417,615** | **0.2825ms** | **1.2643ms** | **15.2587ms** | **121.6569ms** |

이 결과는 로그인과 Heartbeat 부하다. 가챠·인벤토리·길드·전투 등 전체 게임 행동 3만 사용자, 인터넷 접속, 장시간 운영, 최대 수용량 또는 계측 오버헤드를 입증한 것은 아니다. 새 계정 생성이 포함되고 실행 순서·캐시 상태가 다르므로 1천/3만 지연 차이를 규모 증가로 인한 개선이라고 해석하지 않는다.

## APM 수집 실패

| 항목 | 1천 명 | 3만 명 |
|---|---:|---:|
| 저장된 로그인 metric / 실제 성공 응답 | 1,000 / 1,000 | **6,089 / 30,000 (20.30%)** |
| 저장된 Heartbeat metric / 실제 응답 | 3,000 / 3,000 | **105,806 / 417,615 (25.34%)** |
| 기록된 누적 유실 | 858 항목 | **3,323,634 항목** |
| 기록된 HTTP 실패 시도 | 0 | 0 |

‘유실 항목’은 에이전트 큐의 span 또는 자원 샘플 단위이며 요청 수가 아니다. 종료 시 내부 호출도 포함한다. **3,323,634개의 요청이 실패했다는 뜻이 아니다.**

- 1천 명은 로그인·Heartbeat metric이 모두 저장됐다. 접속 유지 중 기록된 유실은 0이었고, 일괄 연결 종료 후 858 항목이 유실됐다.
- 3만 명은 접속 증가·유지 중에도 큐가 약 7,800~8,100개로 포화되고 유실이 계속 증가했다. 종료 전에도 누적 유실이 약 274만 항목에 도달했다. 일괄 종료만의 문제가 아니다.
- 에이전트의 `TryWrite`는 제한 큐가 가득 차면 즉시 유실을 기록한다. 신규 요청 metric은 root span을 전송할 때 생성되므로 root span 유실이 요청 집계 누락으로 이어진다.
- 요청 span, 다량의 Grain/DB/Redis span, 백그라운드 sweep, 자원 지표가 같은 큐를 경쟁한다. 자원 샘플도 제때 수집되지 않아 잠시 오래된 세션 수가 표시됐다.
- HTTP 실패 시도는 0으로 기록됐다. 관측된 직접 원인은 네트워크 오류보다 **공유 큐의 생산 속도와 처리 속도 불균형**이다. 직렬 배치 전송, JSON 처리, EF/SQLite 저장 중 어느 구간이 얼마나 병목인지 정밀 프로파일링한 결과는 아직 없다.
- 마지막 확보한 자원 샘플은 세션 0, 큐 0, 유실 3,323,634였다. 3만 실행의 저장 span은 594,246개다. 유실된 자료를 복구하거나 성공으로 간주하지 않는다.

APM에 남은 지연 분위수와 오류율은 **유실된 일부 표본의 통계**이므로 전체 서비스 지표로 주장할 수 없다. 이 한계 자체가 이번 동접 검증에서 찾은 개선 항목이다.

## 다음 수정 우선순위

1. **요청 집계·자원 상태를 상세 trace 큐와 분리한다.** 처리량/오류/지연 histogram이 내부 span 유실에 함께 사라지지 않도록 한다.
2. **추적 단위의 선택 수집과 예산을 둔다.** 모든 Grain 호출을 무제한 생성해 사후에 일부 span만 버리는 현재 구조 대신, 정상 요청의 샘플링과 오류·느린 요청의 보존 기준을 명시한다. 선택적으로 수집한 수와 장애로 유실한 수를 구분한다.
3. **배치 전송·저장을 프로파일링하고 개선한다.** 같은 시나리오로 계측 ON/OFF, 전송·저장 처리율, 유실률, 완전한 trace 비율을 비교한다. 단순히 큐만 키워 해결됐다고 주장하지 않는다.

이번 요청에서는 제품 수집 정책을 바꿔 결과를 덮지 않았다. 측정 도구와 결과 문서만 추가했으며 발견한 실패를 보존했다.

## 재현·증거

APM 저장소에서 `dotnet build tools/verification/ConcurrentLoad -c Release` 후 격리된 서버에 실행한다:

```powershell
dotnet tools/verification/ConcurrentLoad/bin/Release/net10.0/ConcurrentLoad.dll `
  --count 30000 --rate 3000 --hold 60 --heartbeat 5 --port 9129 `
  --run '<서버 APM_RUN_ID와 동일한 실행 ID>' --output '<새 결과 파일 경로>'
```

도구는 loopback에만 연결한다. 실제 격리 DB에 새 시험 계정을 생성하므로 운영 DB를 대상으로 실행하지 않는다. 출력 파일을 덮어쓰지 않으며 출력 디렉터리는 먼저 준비한다. 서버의 `APM_RUN_ID`를 같은 값으로 설정하고 초기화 API 대신 새 실행 ID로 결과를 구분한다.

- 예비 Run: `concurrency-1000-20261026T100927Z`
- 본 Run: `concurrency-30000-20261026T101028Z`
- 비공개 자료: `.local-evidence/2026-10-26-concurrency/manifest.json`
- 포함 자료: 초 단위 클라이언트 로그/최종 결과, OS TCP 샘플, 게임 로그, 설정과 DLL 해시, APM 집계/자원, 읽기 전용 SQLite 스냅샷, 검증 도구 소스 및 실행 스크립트.
- 이전 `.local-evidence/2026-10-26/`, `.local-evidence/2026-10-26-upgrade/`는 수정하지 않는다.

검증 종료 후 부하 클라이언트와 시험 게임 프로세스를 종료하고, 유휴 검증 서버 및 기존 로컬 Gemma 모델을 복구했다.
