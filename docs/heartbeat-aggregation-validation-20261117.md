# Heartbeat 집계 구현과 로컬 전후 검증

검증일: 2026-11-17. 로컬 Windows 단일 호스트에서 새로 실행한 결과다. GitHub Actions, 원격 배포, LLM 정확도 평가를 수행한 기록이 아니다.

## 변경 이유와 구현

직전 ON/OFF 검증에서는 APM ON 시 게임 메모리와 수집기 비용이 크게 늘었다. 기본 요청의 대부분을 차지하는 정상 Heartbeat를 요청별 metric+entry span으로 저장하고 있었으므로, 정상 신호를 통계로 묶고 조사할 필요가 있는 요청은 상세로 남기도록 변경했다.

- 성공·100ms 미만·내부 오류 없음·지정 유저 아님인 Heartbeat는 5초 구간의 건수, 소요시간 합, 최소·최대, 지연 히스토그램으로 저장한다.
- 오류·시간 초과·느린 요청·지정 유저는 상세로 보존한다. 거절·취소·결과 미확인 Heartbeat도 개별 기록으로 남긴다. 1초 유예 안에 늦게 도착한 내부 오류도 상세 보존으로 전환한다.
- 개별 metric과 집계 Count는 서로 중복되지 않는다. 대시보드 통계와 이상 탐지 기준선은 두 경로를 합산하며, 재전송 시 batch receipt와 집계 ID로 중복을 막는다.
- 게임의 동시 trace 버퍼는 4,096→16,384개로 조정했다. trace별 내부 구간 64개 및 기존 전송·스풀 상한은 유지한다. 한도를 넘으면 상세 제한 상태가 남는다.

설정·자료 구조·복구 한계는 APM 저장소의 `docs/heartbeat-aggregation-guide.md`에 정리했다. 핵심 구현은 `HeartbeatAggregate.cs`, `LocalTelemetry.cs`, `TelemetrySender.cs`, `TelemetryBatchWriter.cs`, `MetricsController.cs`, 게임 서버 `ApmReporter.cs`다.

## 실제 비용 비교

전·후·후·전·전·후 순서로 각각 3회 새로 실행했다. 모든 실행에서 3만 동접을 120초 유지하고 접속 실패·로그인 실패·비정상 종료는 0이었다. 두 조건 모두 APM ON이며, 이전 ON/OFF 자료의 수치를 이번 표에 재사용하지 않았다.

각 실행의 유지 구간 CPU·메모리를 산출한 뒤, 조건별 3회 중앙값을 비교했다.

| 지표 | 개선 전 | 집계 적용 후 | 변화율 |
|---|---:|---:|---:|
| 게임 CPU (% 전체 논리 CPU 용량) | 4.693 | 4.419 | -5.8% |
| 수집기 CPU (%) | 4.100 | 0.454 | -88.9% |
| 게임+수집기 CPU (%) | 8.835 | 4.873 | -44.8% |
| 게임 작업집합 (MiB) | 2,274.4 | 2,291.8 | +0.8% |
| 수집기 작업집합 (MiB) | 605.5 | 182.0 | -69.9% |
| 프로세스 작업집합 합계 (MiB) | 2,879.9 | 2,472.0 | -14.2% |
| Heartbeat RTT p99 (ms) | 43.34 | 26.48 | -38.9% |
| 유지 구간 응답/초 | 5,980.2 | 5,990.1 | +0.2% |
| 패킷 1,000건당 통계 행 수 | 1,000.00 | 39.16 | -96.1% |
| 패킷 1,000건당 논리 DB 크기 (MiB) | 0.972 | 0.051 | -94.8% |

CPU는 외부 Win32 누적 CPU 시간 차이/실측 구간/16 논리 CPU로 계산했다. 메모리는 시간 가중 평균 작업집합이다. 프로세스 작업집합 합계는 공유 페이지를 중복 포함할 수 있으며 물리 RAM 절약량과 같지 않다. p99는 실행별 클라이언트 RTT p99의 중앙값이며, 전체 표본을 합친 백분위가 아니다. 집계 히스토그램의 p99와 별도다.

| 실행 | 실제 유지(초) | RTT p99(ms) | 게임 CPU(%) | 수집기 CPU(%) | 집계된 Heartbeat |
|---|---:|---:|---:|---:|---:|
| hb01_before | 120.005 | 43.34 | 4.459 | 3.901 | 0 |
| hb02_after | 120.004 | 15.11 | 4.341 | 0.393 | 778,563 |
| hb03_after | 120.015 | 26.48 | 4.419 | 0.454 | 768,134 |
| hb04_before | 120.011 | 10.53 | 4.693 | 4.528 | 0 |
| hb05_before | 120.015 | 60.61 | 4.735 | 4.100 | 0 |
| hb06_after | 120.014 | 30.64 | 4.568 | 0.473 | 767,758 |

RTT p99 범위는 기존 10.53–60.61ms, 집계 적용 15.11–30.64ms였다. 고정 5초 Heartbeat를 반복하는 닫힌 부하이며 최대 TPS나 전체 게임 콘텐츠 성능을 의미하지 않는다.

## 요청 수와 상세 보존 대조

준비 실행 1,000명의 로그인·Heartbeat도 포함해 패킷 4,839,641건을 대조했다. 개선 후 정상 Heartbeat 2,314,455건은 집계 Count로 보존했다. 개별 metric의 trace ID 집합과 packet entry span 집합은 실행마다 일치했고, 누락·중복 ID는 0이었다. 집계 히스토그램 합도 Count와 일치했다.

| 실행 | 로그인 | 전체 Heartbeat | 개별 Heartbeat | 집계 행 수 | 클라이언트 대조 |
|---|---:|---:|---:|---:|---|
| hb01_before | 31,000 | 782,780 | 782,780 | 0 | 일치 |
| hb02_after | 31,000 | 778,574 | 11 | 308 | 일치 |
| hb03_after | 31,000 | 768,146 | 12 | 283 | 일치 |
| hb04_before | 31,000 | 781,793 | 781,793 | 0 | 일치 |
| hb05_before | 31,000 | 774,580 | 774,580 | 0 | 일치 |
| hb06_after | 31,000 | 767,768 | 10 | 298 | 일치 |

여섯 실행의 최종 `RequestsDropped`, `DetailsDropped`, `FailedBatches`, 남은 스풀 배치는 모두 0이었다. 이는 기본·선택 상세 전송의 관측 결과다. 모든 내부 호출을 전량 저장했다는 뜻이 아니다. 표본 선택, 64구간 상한, 유예 이후 미연결 구간은 별도로 기록되며, 공개 JSON의 실행별 상태를 참조한다. 전체 게임 로그에서 탐지된 런타임 정체 관련 경고 건수는 0건이다. CPU·지연 비교는 클라이언트가 3만 동접을 유지한 구간만 사용했다.

실제 부하에서 100ms 이상 걸린 Heartbeat 33건(11·12·10건)은 모두 `retained` 상태였으며, 기대한 내부 구간 수와 저장된 구간 수가 일치했다. 이 33건의 상세 상한 생략은 0이었다. 주입 오류 검사는 아래 기능 검사와 구분한다.

## 기능 검사와 이전 자료 보존

- 신규 Agent/실제 SQLite 검사 38개 통과: 정상 1,000건 집계, 오류·내부 오류·늦은 내부 오류·느린 요청·지정 유저·뒤늦게 확인된 유저 식별자·거절·취소·미확인 결과의 상세 보존, 합산 통계, 재전송 및 중복 방지, 잘못된 히스토그램 거부, 구형 수집기 거부 시 유실 건수, 스풀 재시작 복구.
- 실제 게임 서버에서 본 실행 100명 접속 검증(준비 실행 1,000명의 로그도 합산): 지정 유저 Heartbeat trace 3건과 각 내부 구간 보존, 나머지 정상 Heartbeat 2,297건 집계. SQL/Redis와 실제 TCP 경로를 통과했다.
- 기존 Agent·SenderRecovery·CollectorWriter 검사, HTTP 계약 검사, 대시보드 lint/build 통과.
- 서버 통합 검사 40,298 assertions 및 실제 강제 종료/재시작 복구 통과. CPU 측정 회귀의 정상·503 응답 두 조건도 통과. 강제 종료 검사는 기존 게임 데이터 복구 검사이며 집계 버퍼의 강제 종료 무손실 검사가 아니다.
- 과거 DB를 복사한 뒤 실제 수집기로 마이그레이션했다. 원래 열 기준 메트릭 66,866행·분석 4행의 내용 해시 일치, 원본 DB 파일 SHA-256 불변.
- 기존 문서·공개 집계·비공개 manifest와 서버의 사전 미커밋 파일 총 47개의 해시를 변경 전후 대조했다. 기존 검증 기록과 사용자 변경은 그대로 보존했다.

## 트레이드오프와 검증 범위

정상 Heartbeat의 유저별 개별 이력을 나중에 복원할 수 없다. 문제 유저는 `APM_TRACE_USER_IDS`로 서버 시작 전에 지정해야 한다. 대시보드 필터는 조회 기능이며 수집 정책 변경 기능이 아니다. 다른 게임 패킷과 중요 요청의 기존 수집 정책은 유지한다.

건수와 평균은 실제 Count·소요시간 합으로 계산한다. 집계가 섞인 경로의 백분위는 히스토그램 구간 상한 추정으로 바뀌며, API와 UI에 이를 표시한다. 시간 필터 경계에는 5초 구간 단위 오차가 있다. 상세를 1초 기다리는 메모리 비용과 16,384개 버퍼의 상한도 함께 고려해야 한다.

메모리 집계를 요청마다 동기 디스크 저장하지 않는다. 정상 종료는 flush하지만 강제 종료 전에 내보내지 못한 집계는 유실될 수 있다. 이번 비교는 전송을 비운 후 종료했으며 무제한 장애 내성·상용 APM 동등성을 주장하지 않는다.

부하 생성기·게임·DB·수집기는 같은 PC에 있다. 이전 3만 TCP 연결 정리와 다음 측정이 겹치지 않도록 TIME_WAIT 2,000개 미만을 두 번 확인했다. Windows 커널 내부 원인을 고친 것은 아니며, 분리 호스트 재검증과 전체 콘텐츠 혼합 부하는 남아 있다.

## 실패와 수정 이력

첫 두 기능 검사에서는 던지지 않은 합성 예외의 빈 스택 문자열 때문에 상세 배치가 거부됐다. 빈 스택을 null로 정규화해 수정했고, 실패 DB와 거부된 배치를 보존했다. 이후 3차 검사와 구형 수집기 거부 검사를 추가한 4차 검사를 통과했다.

첫 서버 검사 준비에서는 DB 이름이 기존 안전 규칙의 `trickcal_checks_` 접두사를 충족하지 않아 DB 변경 전에 거부됐다. 새 격리 환경과 올바른 이름으로 재실행했다. 최초 마이그레이션 비교도 새 열을 원래 열과 함께 비교하는 스크립트 오류로 실패했으며, 원본의 열 목록을 고정해 별도 사본으로 통과했다. 이 실패들도 삭제하지 않았다.
