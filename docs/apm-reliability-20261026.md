# APM 수집 신뢰성 개선·3만 동접 재검증 — 2026-10-26

## 판정

**최종 실행에서 30,000명의 동시 로그인을 60.0024초 유지했고, 로그인 30,000건과 Heartbeat 414,969건의 기본 기록을 전량 수집했다. 에이전트에 기록된 기본 요청·상세 전송 유실과 HTTP 실패 시도는 모두 0이었다.**

기본 기록은 모든 요청의 소요 시간·결과·trace·가명 유저·세션이다. 내부 호출 상세는 정상 요청의 1% 및 요청 종료 시 오류/100ms 이상으로 선택한 trace만 보존한다. **모든 내부 호출을 전량 저장한 시험이 아니다.** 상한 생략·표본 제외를 유실 0과 혼동하지 않는다.

**같은 최종 코드의 직전 실행에서는 긴 런타임 정체와 함께 기본 기록 3,154건이 유실됐다.** 따라서 최종 무손실 실행만으로 장애 내성이나 반복 무손실을 주장하지 않는다. 지속적인 수집 처리량 부족과 초기 상세 집중은 개선했지만 긴 실행 정체·수집기 장애에도 견디는 영속 재전송은 남은 과제다.

최종 Run: `reliability-30000-20261026T111916Z`. 완료 UTC: `2026-10-26T11:20:41.1244889Z`. 이전 [3만 동접 수집 실패](concurrency-validation-20261026.md)는 그대로 보존하며 이번 성과로 덮어쓰지 않는다.

## 변경한 구조

1. 기본 요청·작업 기록과 상세 trace의 제한 큐/전송기를 분리했다. 자원·수집 상태는 별도 전송 경로를 쓴다. 상세 기록 과부하가 기본 통계를 밀어내던 연결을 끊었다.
2. 정상 상세 1%, 오류 또는 100ms 이상 요청은 우선 보존 대상으로 선택한다. 선택은 요청 종료 시점의 관측값을 기준으로 한다. 동시 버퍼 4,096 trace, trace당 내부 span 64개, 기본 큐 32,768개, 상세 큐 32,768 span, 최대 배치 256개로 제한했다. 임의의 부하에서 무손실을 보장하지 않는다.
3. Redis profiling은 부모 요청 종료 뒤 Activity를 전달할 수 있다. 게임 Redis flush를 100ms로 설정하고 선택된 trace는 종료 후 약 1초 동안 늦은 span을 기다린다. 기본 기록은 즉시 전송하고 상세 메타데이터만 나중에 갱신한다. 두 전송의 도착 순서가 바뀌어도 최종 상태가 pending으로 되돌아가지 않으며 metric을 중복 생성하지 않는다.
4. SQLite는 단일 쓰기 트랜잭션 안에서 prepared INSERT를 재사용한다. 배치 ID 중복 방지와 데이터 저장은 같은 트랜잭션이다. EF 모델/보강 스키마가 같은 열에 만든 중복 인덱스 2개를 정확한 정의를 확인한 뒤 정리한다.
5. 쓰기 연결은 `synchronous=FULL`을 유지한다. 캐시 32MiB, WAL 자동 체크포인트 16,384페이지, journal size limit 64MiB를 적용했다. 뒤의 값은 WAL 파일의 절대 상한이 아니며 장시간 읽기 중에는 커질 수 있다. 내구성을 낮춰 응답을 앞당긴 변경은 아니다.
6. 상세 큐는 한 묶음에 여러 span을 담는다. 전송 대기 판단을 묶음 수에서 실제 span 수로 수정했다. 초기 로그인 집중량을 수용하도록 상세 예산을 8,192→32,768로 조정했다. 요청 큐 분리·선택 수집·저장 개선과 함께 적용한 결과이며 큐 확대 단독 효과로 주장하지 않는다.

화면에는 기본 관측/전송/대기/유실, 상세 표본 제외/상한/유실을 따로 표시한다. 요청 상세에는 `sampled_out`, `pending`, `retained`, `truncated`, `buffer_limit`, `queue_dropped` 상태를 표시하고 5초마다 갱신한다. 카운터는 프로세스 인스턴스별이며 예전 기록에는 새 항목이 없다.

별도 DB 사본의 쓰기 실험에서 128개 배치의 행 삽입 누적 약 779ms, 커밋 약 2,318ms를 관측했다. 배치 128→256만 변경하거나 중복 인덱스만 제거한 실험으로는 충분한 개선이 없었다. 캐시/체크포인트 조정도 함께 검토했다. 실험 순서·캐시 상태가 달라 개별 설정의 인과 효과나 일반 성능 수치로 사용하지 않는다. 벤치마크 코드와 원시 시간은 비공개 증거에 있다.

개발 중 Redis 상세가 빠지는 실제 게임 회귀 실패도 발생했고, 늦게 도착하는 Activity 처리 후 통과했다. 이를 과거 자연 발생 서버 장애로 표현하지 않는다.

## 조건·검증 범위

같은 Windows PC, 약 31.11GiB RAM, loopback, 게임/수집기 Debug·부하 도구 Release, 단일 게임 서버. 목표 증가율 3,000명/초, 전체 로그인 후 60초 유지, 각 연결의 Heartbeat 응답 후 5초 간격이다. 실제 준비 시간은 목표 증가율의 역산과 다르다. 기존 ConcurrentLoad 도구와 클라이언트 시나리오는 변경하지 않았다. PostgreSQL 15439·Redis 16389의 별도 시험 인스턴스를 사용했다. 새 계정이 누적되고 캐시·실행 시점이 달라 지연 개선을 APM 단독 효과로 주장하지 않는다.

부하 중 LLM은 언로드했다. 검사 후 기존 Gemma 모델을 복구한다. 동시 LLM 추론, 전체 게임 플레이 3만 명, 인터넷 지연, 장시간 운영, 최대 수용량, APM ON/OFF 오버헤드는 이번 결과로 입증하지 않는다. 디스크 영속 재전송 큐·다중 수집기·상용 운영 수준의 권한 관리는 아직 없다. 수집기 장기 장애나 상한 초과 시 유실이 가능하며 상태를 명시한다. 1초보다 늦은 의존 span과 요청 종료 후 발생한 오류의 소급 선택도 보장하지 않는다.

회귀 검사: 에이전트 25항목, API 25항목, 실제 게임 19항목. 오류/느린 trace 선택, 상한 표시, 상세 큐 포화 시 기본 기록/자원 전송 유지, Redis 지연 도착, 메타데이터 순서 역전·중복 방지, 상세 묶음 대기 조건을 포함한다. 이전 실검증 원본과 평가 사례 12개는 보존한다. 이번 작업에서 파인튜닝은 하지 않았다.

## 증거와 재현

최종 회귀 후 로컬 Gemma 모델을 기존 GPU/context 설정으로 복구했다. 새 DebugHandler 주입 오류 trace `626c7d5ed5e31e6bc31742ee4eb3c9ed`의 근거·현재 소스·분석 답변 저장을 확인했다(서버 측 분석 12.063초). 답변은 IsAdmin=false에 따른 예외를 설명했지만, 권한 검사 전에 재화를 지급하는 핵심 순서 문제를 명확히 지적하지 않았다. 분석 호출 성공과 진단 정확도는 구분하며 이 답변도 그대로 보존한다. 앞선 v2의 다른 답변과 합쳐 성공 사례로 바꾸지 않는다.

게임·수집기·대시보드 빌드는 성공했고 lint는 오류 0, 기존 경고 2개였다. 마지막 수집기 빌드에는 종료 중인 프로세스의 DLL 잠금으로 복사 재시도 경고 1개가 있었고 재시도 후 성공했다. 실행 DLL 해시를 각 부하 설정에 기록했다.

- 비공개 보존본: `.local-evidence/2026-10-26-reliability/manifest.json`.
- 모든 중간/최종 실행의 client 결과·초 단위 진행 로그·OS TCP·runtime·설정·DLL 해시, 각 수집 DB, 회귀 결과, 저장 실험 코드/결과, 소스 스냅샷과 화면을 포함한다.
- 원래 DB 2개의 SHA-256 불변 및 사본 마이그레이션의 기존 행 digest를 확인한다. 이 파일들이 외부 포트폴리오 공개 자료라는 뜻은 아니다.
- 이전 보존본 무결성 대조: 최초 54개·v2 67개 파일은 그대로다. 이전 동접 manifest의 27개 항목 중 실제 증거 파일 25개는 해시가 일치한다. 나머지 2개는 SQLite가 연결 종료 시 제거하는 32KiB SHM과 빈 WAL로, 이전 manifest가 임시 파일까지 포함했던 기록 문제다. 원 DB 스냅샷 해시는 일치하며 이전 manifest를 덮거나 임시 파일을 재생성하지 않았다. 이번 manifest에는 이 차이를 명시하고 새 DB 스냅샷은 연결을 닫은 뒤 임시 파일을 제외해 확정한다.
- [실행 안내](apm-v2-runbook.md)의 격리 환경에서 ConcurrentLoad를 실행한다. 기본 상세 정책은 `APM_DETAIL_SAMPLE_RATE=0.01`, `APM_SLOW_TRACE_MS=100`이다. 모든 내부 구간을 검사하는 소규모 `check_game.py`는 서버를 `APM_DETAIL_SAMPLE_RATE=1`로 실행한다.

포트폴리오 표현: “3만 동접 실험에서 발견한 지속적인 APM 수집 누락을 요청/상세 큐 분리, 명시적 상세 선택, 배치·저장 개선으로 줄였습니다. 최종 60초 유지 시험에서 로그인 3만 건과 Heartbeat 414,969건을 대조해 기본 기록 100% 수집을 확인했습니다. 같은 코드에서 긴 런타임 정체 시 유실된 실행도 보존하고, 상세 표본 제외·상한 생략·전송 유실과 남은 장애 내성 과제를 구분했습니다.”
